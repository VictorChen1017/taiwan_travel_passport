## 克服的難題

- 相鄰村里的界線對不上（舊檔各區域各自簡化，共用邊被簡化成兩條不同的線，地圖有縫、判定有漏）→ 改用內政部未簡化原檔，匯入時 `ST_CoverageClean` 整理成不留縫，匯出時 `ST_CoverageSimplify` 整層一起簡化，共用邊只簡化一次；敘述見 [records/2026-11-26-02-界線不留縫簡化.md](records/2026-11-26-02-界線不留縫簡化.md)

迷霧地圖手機效能的整段優化過程（使用者在意什麼、為什麼 Canvas 在手機上快、每一步做了什麼）見 [records/2026-11-26-02-迷霧地圖手機效能.md](records/2026-11-26-02-迷霧地圖手機效能.md)。重點：

- iPhone 村里地圖點選破圖 → 先確認界線資料沒有縫，判斷是 iOS 局部重畫大型 SVG 漏畫；外框改畫在獨立疊層，不再動到大地圖
- 外框一邊深一邊淺 → 原因是後畫的鄰居蓋住外框；同樣用疊層解決
- 拖曳卡頓 → 手勢中只用 CSS transform 移動已畫好的地圖，放手才重畫一次
- 村里補點等很久、拖久了卡死 → 量測發現計算只要 0.1 秒，慢在重建約 8,000 個 SVG 元素；村里層改用 Canvas，重畫約 6 毫秒（電腦量測），只畫畫面內的區域

## 對話檢討

- 做得好的：每次先量測或檢查再下判斷（單獨畫出區域排除資料問題、加計時找出慢在繪製而不是計算）；要決定的事用選項一次問完，維護者選完就做
- 要改進的：補點第一版只在電腦驗證，手機的破圖、卡頓都要等維護者實機回報才發現；預覽窗格把畫面更新限制在每秒約一格，量不到真正的繪製時間
- 下次的做法：牽涉大量 SVG 元素或手勢的功能，一開始就把 iOS 的繪製成本納入設計；手機上的效能以維護者實測為準，日誌中分開寫「程式時間」和「實機感受」
