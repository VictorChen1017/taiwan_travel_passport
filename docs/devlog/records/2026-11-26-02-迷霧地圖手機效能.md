# 迷霧地圖的手機效能優化（2026-11-26）

這份紀錄說明迷霧地圖從「iPhone 上破圖、卡頓、甚至卡死」到「體驗好非常多」（維護者實機回饋）的過程：問題怎麼被發現、為什麼會這樣、每一步做了什麼，以及最後為什麼選 Canvas。commit：`1a05e96`、`8a115a4`。

## 使用者在意的是什麼

迷霧地圖是這個網站最「好玩」的地方：打開地圖、拖來拖去，看自己點亮了哪些地方，再順手把漏掉的村里補上。使用者在意的不是演算法，而是幾個很直接的感受：

- **手指一動，地圖就要跟著動。** 拖曳、雙指縮放只要延遲一下，就會覺得「卡」；卡到沒有反應，使用者會以為網站壞了。
- **點下去要馬上有回應。** 補點按了「加入」，如果幾秒都沒動靜，會懷疑有沒有按到、會不會重複加。
- **畫面不能壞。** 地圖上突然空白一條（破圖）、外框一邊深一邊淺，都會讓人覺得粗糙、不可信。
- **大部分人用手機看，而且多半是 iPhone。** 電腦上順不代表手機上順；這次的問題全都是手機才看得出來。

村里地圖是低頻使用的功能（維護者也這麼說），但正因為少用，偶爾打開時更不能讓人留下「很卡」的印象。

## 問題是怎麼浮現的

維護者在 iPhone 上實際使用，依序回報了四個現象：

1. 村里地圖點一下某個村里，畫面出現一條水平空白（破圖）
2. 滑過或點選時，區域的外框顏色不均：有的邊很深、有的邊幾乎看不見
3. 拖曳、縮放卡卡的；村里地圖拖一段時間後整個卡住
4. 在村里地圖補點，按下「加入」後要等很久才有反應

## 先確認：是資料壞了，還是畫的方式有問題？

破圖第一個要排除的是資料。剛換過內政部未簡化的界線，有沒有可能村里之間留了縫？用電腦瀏覽器把同一塊區域（高雄旗山區南勝里一帶）單獨畫出來放大檢查，村里之間是密合的，沒有縫。而且截圖上的空白是一條**水平的長方形帶**，橫跨好幾個村里——真正的資料缺口不會長成這種形狀。結論是「畫的方式」出了問題，不是資料。

## 根本原因：一張有 8,000 個區域的 SVG

迷霧地圖原本用 SVG 畫：每個村里是一個 `<path>` 元素，村里層一共約 8,000 個。SVG 的好處是每個區域都是網頁元素，滑過、點選、上色都很方便；壞處是**瀏覽器要把 8,000 個元素當成網頁的一部分來管理**——記住每個元素的樣式、算出它在哪裡、需要時重畫它。

這在電腦上還撐得住，在手機上就處處碰壁：

- **點選時只改一個區域的樣式，瀏覽器卻要重畫一大塊。** 舊做法是替被選的區域加上外框樣式。iOS 會重畫那一塊範圍，而那塊範圍裡疊了大量其他區域，重畫時漏畫，就留下空白一條（破圖）。
- **外框被鄰居蓋住。** 外框畫在區域自己身上，SVG 照順序畫，後面才畫的鄰居會蓋住外框的一半，所以外框一邊深一邊淺。
- **拖曳時每一格畫面都重畫整張地圖。** 舊做法在手指每移動一下就改地圖的視窗（viewBox），瀏覽器就得把 8,000 個區域整張重畫一次。手機一秒要畫 60 格，根本畫不完，所以卡。
- **iOS 會把大型 SVG 做成 GPU 圖層。** 拖曳時 iOS 把整張 SVG 轉成一張圖片交給顯示晶片移動，放開手又整張重畫、重新做圖層。地圖越大、拖越久，記憶體壓力越大，最後整個卡住。
- **補點後整張地圖重建。** 量測（電腦、原專案 27,559 張照片）：補一個點，重新計算成就只要約 0.1 秒，程式合計約 0.2 秒；慢的是之後**把整張村里 SVG 拆掉重建**，瀏覽器要重新解析、排版、繪製 8,000 個元素。手機上這一段會再慢好幾倍，就是使用者感受到的「等很久」。

## 做了哪些優化（依序）

### 1. 外框改畫在獨立的疊層（解決破圖、顏色不均）

滑過或點選時，不再改地圖上區域本身的樣式，而是在地圖上面疊一張幾乎是空的小 SVG，只在裡面畫一條被選區域的外框。

- 外框在最上層，不會被任何鄰居蓋住 → 四周粗細、顏色一致
- 大地圖本身完全沒變 → iOS 不需要重畫大地圖，也就沒有漏畫的機會

外框樣式由維護者選了「平面深色」，比陰影輕，在 iOS 上最順。

### 2. 手勢進行中只「移動圖片」，放手才重畫（解決拖曳卡頓）

拖曳、雙指縮放時，不再每一格都改地圖視窗，而是用 CSS transform 把**已經畫好的地圖當成一張圖片**平移、縮放。這件事由顯示晶片負責，幾乎不花時間。手指放開後，才真正改一次視窗、重畫一次。

代價是手勢進行中拖到原本畫面外的地方會先是空白，縮放時線條會暫時變粗或變細，放開後就恢復——這是地圖類 App 常見的做法，使用者幾乎不會在意。為了確保「移動中」和「放開後」的位置完全一致，用電腦瀏覽器量過同一個區域在兩種狀態下的位置，分毫不差。

### 3. 村里層改用 Canvas 繪製（解決補點慢、拖曳久了卡死）

前兩步之後鄉鎮、縣市已經很順，但村里層還是太重：只要地圖還是 8,000 個 SVG 元素，重建、重畫、做 GPU 圖層的成本就在那裡。維護者選了根治的做法：**只有放大地圖的村里層改用 Canvas**。

**為什麼 Canvas 在手機上快很多？**

- **Canvas 是一張圖，不是 8,000 個元素。** SVG 的每個區域都是網頁元素，瀏覽器要替每一個記樣式、算位置、管理重畫範圍；Canvas 只是一塊畫布，程式直接告訴它「在這裡塗這個顏色」，畫完就只剩像素。瀏覽器要管理的東西從 8,000 個變成 1 個。
- **重畫是一次性的、可控的。** 需要更新時把整張畫布清掉重畫，不會有「只重畫一小塊結果漏畫」的問題，也就不會破圖。
- **只畫看得到的部分。** 每個村里事先算好外框範圍，重畫時畫面範圍外的直接跳過；放大到某個縣市時，實際只畫幾百個村里。
- **補點不必重建任何東西。** 加完點只要換掉一個顏色、重畫畫布。電腦上整張村里畫布重畫的程式時間約 6 毫秒，原本是拆掉重建整張 SVG。
- **GPU 圖層小而固定。** 畫布的大小就是螢幕上那個框的大小，不會因為地圖複雜而變大，拖久了也不會吃光記憶體。

**怎麼做到「看起來和用起來都一樣」？**

改成 Canvas 最大的挑戰是：畫布上的區域不再是元素，沒辦法直接知道手指點到誰。做法是：

- 原本的 SVG 留著但清空，疊在畫布上方，只負責接收觸控、滑鼠，並提供「目前視窗」給畫布和外框疊層共用，三者永遠對齊
- 點選、滑過時，先用每個村里的外框範圍篩掉不可能的，再用瀏覽器內建的「這一點在不在這個形狀裡」精確判斷
- 區域直接用原本的 SVG 路徑字串建立（瀏覽器的 Path2D 可以直接讀），顏色、界線、海岸線都照原本的設定，所以外觀和 SVG 版相同
- 泡泡、補點流程、外框疊層完全沿用；手勢中畫布跟著 transform 移動，放開才重畫；手機轉向、切換深淺色時也會重畫
- 縣市、鄉鎮與頁面上的小地圖區域少，維持 SVG

### 4. 其他配合的小改動

- 補點按下「加入」時，按鈕立刻變成「加入中…」，讓使用者知道已經在處理
- 補點表單的說明文字整段拿掉（維護者決定），泡泡更精簡，手機上不再擠成一大塊
- 海改成側邊欄的淺藍、海岸線加粗（匯出時把同一層區域合併成一條海岸線，和界線完全對齊）

## 學到的事

- **手機的瓶頸常常不在計算，而在「畫」。** 這次的計算一直只要 0.1 秒，真正慢的是瀏覽器處理大量 SVG 元素。量測時要分開看「程式跑多久」和「畫面多久才更新」。
- **先排除資料，再懷疑繪製。** 把同一塊區域單獨畫出來檢查，幾分鐘就能確定不是界線資料的問題，避免白白重匯圖資。
- **同一個修法可以解決好幾個問題。** 外框疊層同時修好破圖與顏色不均；Canvas 同時修好補點慢與拖曳卡死。
- **電腦驗不到手機的感受。** 開發用的預覽窗格把畫面更新限制在約每秒一格，量不到真正的繪製時間；iOS 的破圖與卡死也無法在電腦重現。最後的判斷一定要靠維護者用 iPhone 實測——這次的回饋是「體驗好非常多」。
