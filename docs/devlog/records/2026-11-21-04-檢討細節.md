## 一、等待時間從哪裡來

| 來源 | 這一輪的情況 | 估計影響 |
|---|---|---|
| 一次寫出大檔案 | `js/report.js`（約 600 行）、`help.html`、`js/shared.js` 都是一次寫完；產生期間畫面上沒有任何進度 | 最大。一個大檔就要數分鐘，這段時間看起來像「卡住」 |
| 瀏覽器測試的來回次數 | 報表測試約 20 次截圖；每次「截圖 → 看圖 → 下一步」都是一個完整來回 | 大。截圖本身很快，慢在每次來回都要重新處理整段對話 |
| 寫死的等待 | 每次重新整理都 `setTimeout` 等 1.5 秒＋載入測試資料 6 秒＋開報表 1.5～2.5 秒；這一輪重新整理約 6 次 | 中（合計約 1 分鐘以上） |
| 瀏覽器快取 | 改了 `js/app.js`，瀏覽器沿用舊檔，多跑了 2 輪測試才發現要更新版本參數 | 中 |
| 開工前讀檔 | 一開始完整讀 SPEC（約 45 KB）與多個程式檔 | 小～中（主要是 token，見第二節） |
| 工具失誤 | bash heredoc 解析失敗重寫一次；一次 grep 把 94 KB 的 `rail.json` 整個印出來 | 小 |

### 可以縮短的做法

1. **測試資料自動載入＋等條件而不是等秒數**：網址 `?dev=legacy` 啟動時自動載入測試資料，並提供 `__fogDev.ready`（計算完成才 resolve）；測試腳本 `await` 它，取代固定的 6 秒等待。
2. **開發用伺服器不快取**：寫一個 `tools/dev_server.py`（送 `Cache-Control: no-store`），開發時不必一直改版本參數，也不會測到舊檔；正式改版時仍要更新 `index.html` 的版本參數（GitHub Pages 會快取 10 分鐘）。
3. **自動檢查頁取代大部分截圖**：`dev/selftest.html` 一次跑完手動紀錄、備份往返、報表產生等檢查，回傳一張通過／失敗表；一次呼叫取代十幾次來回。截圖只留給最後的外觀確認，並縮小（scale 0.6）、用 batch 一次做多步。
4. **大檔案分段寫、邊寫邊回報**：總產生時間省不了多少，但每段完成都有進度，不會出現十幾分鐘沒有消息；也比較早發現方向錯誤。
5. **決定一次問完**：這一輪已經做到（每個功能開工前一次問 3～4 個問題），維持。

## 二、token 用量與什麼時候換新對話

### 費用怎麼來

- 每一次來回都會把「整段對話＋系統設定＋專案說明」重新送一次。對話有快取，重複的部分比較便宜，但仍然隨對話長度線性增加；對話越長，每一步都越貴。
- 固定成本：**這一輪的工作目錄是舊專案 `photo_monitor_ver202611`，所以舊專案的 `CLAUDE.md`（約 19 KB）每一次來回都會帶著**，但內容幾乎都和新專案無關。這是目前最大、最容易省的浪費。
- 換新對話的成本：重新讀「接手需要的資料」。現在要讀 SPEC（45 KB）＋記憶，約 1.5 萬 token；如果有一份精簡的接手文件，可以降到幾千 token。

### 建議的切換時機

| 該換 | 不該換 |
|---|---|
| 一個功能完成、已 commit、日誌與 SPEC 寫好之後 | 功能做到一半、除錯到一半（換了要重新理解，反而更貴） |
| 下一件事不需要這一輪的細節（例如從「寫報表」換到「部署」） | 下一件事就是剛做完的東西的修正 |
| 對話已經被自動摘要過一次（細節已經掉了，不如從文件重新開始） | |

**原則：一個功能一個對話**——討論 → 實作 → 驗證 → commit → 寫日誌，然後開新對話。以這一輪來說，成就報表 commit 之後就適合換新對話再做說明頁與部署；現在（部署完成、日誌寫好）也是很好的切換點。

### 讓新對話更省的準備

1. **在新專案資料夾開對話**，並在 `photo_fog_static` 放一份精簡的 `CLAUDE.md`（1～2 KB：必守規則、測試方式、文件位置），取代每次都帶著的舊專案說明。
   - 注意：repo 是公開的，`CLAUDE.md` 會被公開；不想公開的內容放 `CLAUDE.local.md`（加進 `.gitignore`）。
   - 注意：記憶資料夾是依工作目錄分開的，換資料夾後舊的記憶不會自動載入，必要的內容要寫進新的 `CLAUDE.md`。
2. **接手只讀三樣**：`CLAUDE.md` → 最新一份開發日誌的「留下的事」→ SPEC 中相關的章節（不要整份讀）。
3. 對話中避免大量輸出：讀檔用行數範圍、搜尋限制筆數、截圖縮小、能用程式檢查的不要截圖。

## 三、本機全端專案移植到 GitHub Pages 要解決的問題

| 問題 | 這個專案的解法 |
|---|---|
| 沒有後端（PHP、MySQL、PostGIS 都不能用） | 維護者在本機用 `tools/export_static.php` 把圖資與成就設定匯出成靜態 JSON；所有計算改在瀏覽器的 Web Worker 進行 |
| 資料存哪裡 | 使用者的匯入結果存在瀏覽器 IndexedDB；換裝置用備份檔（JSON）搬移 |
| 圖資太大 | TopoJSON（共用邊界只存一次、座標量化）、用到才載入；GitHub Pages 自動 gzip（單檔上限 100 MB，最大檔 4.6 MB） |
| 網址在子路徑 `/<repo>/` | 全部用相對路徑；加 `.nojekyll` 讓 Pages 不經 Jekyll 處理 |
| 需要 HTTPS 的功能 | `showDirectoryPicker`、module Worker 都要安全環境；Pages 一律 HTTPS，本機用 `127.0.0.1` 也算安全環境 |
| 帳密與個人資料 | `.env` 不進 repo，程式只讀環境設定；個人測試資料放 `test/` 並加入 `.gitignore`；push 前搜尋追蹤的檔案有沒有帳密 |
| 免費 Pages 需要公開 repo | 確認 repo 裡沒有不能公開的東西（維護工具 PHP 會被當成文字檔公開，內容不能含帳密） |
| 外部套件與服務 | CDN 固定版本；地圖圖磚要遵守供應商政策（OSM 禁止大量使用、要標示來源）；換供應商的設定集中在一處 |
| 快取 | Pages 快取 10 分鐘；ES module 互相 import 沒有版本參數，改版後可能新舊混用 → 改版時更新入口檔的版本參數 |
| 同一帳號的 Pages 共用來源（origin） | `<帳號>.github.io` 下所有專案共用 IndexedDB、localStorage；都是自己的網站風險低，要完全隔離就用自訂網域 |
| 隱私說明 | 沒有後端，但仍有對外連線（GitHub、CDN、圖磚）；在說明頁逐一列出對象、時機、送出內容 |
| 授權 | 政府開放資料、OSM（ODbL）、維基百科、套件授權都要在頁尾與說明頁標示 |
| 部署步驟 | 建公開 repo → `git remote add` → `git push` → Settings → Pages 選分支與資料夾；這台電腦沒有 `gh`，建 repo 與開 Pages 由維護者在網頁上操作 |
| 測試要模擬 Pages | 用不會執行 PHP 的純靜態伺服器測試，才能確認網站真的不依賴後端 |
| 行尾 | Windows 上 git 會提示 LF／CRLF 轉換；不影響網站，但要注意有些檔案（例如舊專案的 `photomap.js`）規定 CRLF |

## 四、下一步建議

1. 維護者開啟 GitHub Pages 後，實測線上版（開新對話做）
2. 新對話開始前：在 `photo_fog_static` 建精簡的 `CLAUDE.md`
3. 實作第一節的 1～3 項（測試資料自動載入、不快取的開發伺服器、自動檢查頁），之後每次測試都能省時間
